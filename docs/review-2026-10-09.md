# Promptbook — Review of code and documents, 2026-10-09

**Reviewed:** r1.7 at git `953336a`: `src/` (3,568 lines of JavaScript, 281 of CSS), `build.py`, `scripts/`, `test/`, and every document.
**Companion files:** `docs/architecture.md` (the structure this review refers to), `docs/verification.md` (what the checks cover).

Three lists follow: **criticalities** (X: defects and risks to act on), **refactor opportunities** (F: structure that would pay back), **technical debt** (T: what has accumulated around the code). Each entry gives its evidence and a suggested action. Nothing in `src/` was changed by this review.

**Severity.** High: can lose the user's work or the project, or stands between a release and trusting it. Medium: wrong behaviour with a way round, or a cost that grows. Low: housekeeping.

**Evidence.** "Confirmed" means a probe ran the case against the built `promptbook.html` in Chromium and the result is quoted. "Measured" means a number was taken the same way. "From reading" means the code says so and no probe was run.

---

## 1. Summary

The tool does what its specification says, and the automated checks agree: 495 pass, none fail. The parser, the text-edit path and the round trip of the script are solid and well covered. The documents have been unusually honest about what was not verified.

Four things deserve attention before the next rehearsal relies on the tool:

1. **Two boards can end up in one file and one drawing replaces the other** (X1, confirmed).
2. **A damaged settings or ink file opens as empty without a word, and is overwritten at the next change** (X2, confirmed).
3. **The project exists in one folder on one machine**, with no remote and with r1.6 and r1.7 untagged (X3).
4. **The two latest releases changed pointer handling and the show file and have no recorded device trial** (X4).

The main structural cost is that the three source files share one scope, so the layering described in the plan is a convention the code does not keep (F1, F2). The main accumulated debt was in the documents, which this restructuring has paid down (T1).

## 2. What is in good shape

| Area | Why |
|---|---|
| Script round trip | A parse followed by a save returns the same text, checked in unit and browser tests. External editing is safe by construction. |
| One path for every text change | Every edit is "compute a new full text, `commitText`". Undo, saving and redrawing hang off that one function. |
| No HTML injection surface | The code builds the page with `textContent` and `createElement` only. There is no `innerHTML`, `eval` or dynamic script anywhere in `src/`. Script text, cue descriptions and names from a show file cannot run code. |
| Saves are atomic | Files are written through `createWritable`, which replaces the file only when the write completes. An interrupted save leaves the previous file. |
| Outside changes are detected | A replaced show file and an edited `script.md` are noticed before a save, and the user is asked. Checked, including "Keep mine". |
| The history is real git | The checks run `git fsck`, `git log` and `git diff` on what the tool wrote. |
| Strings | 225 keys, each in English and Italian, enforced by a unit check. |
| Tooling | Build, syntax check and unit checks in under a second after every edit; the pre-commit hook refuses a built file that does not match `src/`. |
| Candour | Every release note says what was simulated and what was never tried. |

## 4. Refactor opportunities

Ordered by what they unlock. None changes behaviour.

| # | Opportunity | Evidence | What it buys |
|---|---|---|---|
| F1 | **Make `core.js` independent of the other two files.** It calls up into them from five places: `relayout`, `facingSig`, `closePop` (view) and `markDirty`, `updUndo` (io). | The unit harness has to stub four of them to load the file (`test/unit/_core.js`). | Pass them in as hooks, or have `commitText` raise one "text changed" event. `core.js` then loads in Node as it is, and the "pure, testable" parser of the first plan becomes true for the whole file. |
| F2 | **Split `io.js` and `view.js` along the component table.** `io.js` (959 lines) holds storage, zip, draft and backup, git, two dialogs, Settings, toolbar, keyboard, start screen and the sample. `view.js` (1,431 lines) holds rendering, boards, templates, pointer input, popovers, panels, CSV and print. | `docs/architecture.md` §4 lists 22 components in 3 files. `build.py` already joins a list of files. | Mechanical. Zip and git need only `Blob`, `CompressionStream` and `crypto.subtle`, all present in Node 24: as files of their own they can be unit-tested without a browser, including against damaged input (T9). |
| F3 | **Give the pointer handling an explicit state machine.** One mutable `P` with four kinds (`tap`, `ink`, `erase`, `drag`), three handlers on two targets, and one timer field `lp` that means "long press" (0.56 s) or "hold to lift" (0.3 s) depending on what was hit (`src/view.js:591-735`). | The least testable code is the code most dependent on real hardware (X4). | A pure function from state and event to state and effects can be checked in Node with recorded event sequences, including ones captured on the laptop. |
| F4 | **One function that writes text from blocks.** The same loop (emit the blank lines, emit the block) is written six times. | `src/core.js:614, 622, 638, 649, 675`, `src/io.js:272`. | One place to change how spacing is kept; the r1.6 fix for doubled blank lines had to be made in one of the six. |
| F5 | **Name the things written out again and again.** | A cue looked up by block and offset, inline 10 times in `src/view.js`. "Is anything unsaved" spelled out 5 times in `src/io.js` (lines 165, 216, 254, 279, 548). A fresh dirty-flags object 4 times. `clearTimeout(saveT)` 6 times. The act and scene pass twice (`src/core.js:559`, `811`). The similarity threshold 0.34 twice (`src/core.js:539`, `741`). | `cueAt(id, offset)`, `isDirty()`, `cleanFlags()`: fewer places for the next change to miss one. |
| F6 | **Names.** Globals are single letters (`S`, `P`, `h`, `t`, `$`) and are shadowed. | `P` is the pointer state (`src/view.js:591`) and, elsewhere, a page (`pl`, `paginate`, `renderScriptPage`, `renderFacing`). `h`, the element helper, is a loop variable in `folderFiles` (`src/io.js:380`). `t`, the translate function, is a table inside `CRC_T` (`src/io.js:56`). `r2` and `pl`, both helpers, are buttons in `openCueEdit` (`src/view.js:1078-1082`). `sv` is the SVG helper and also a field of a block. | With one shared scope, a shadowed global is a bug waiting for an edit. Rename the locals at least. |
| F7 | **One place for thresholds.** Three are named (`DRAG_HOLD`, `DRAG_EDGE`, `DRAG_REACH`); the rest are literals: 8 px, 350 ms, 450 ms, 40 px, 560 ms, 420 ms, 700 ms. The specification quotes several by value. | `docs/specs/05-input.md`, Consequences, lists seven. | Tuning on the device (X4) becomes editing one block; the specification can cite names. |
| F8 | **Narrow what the tests may see.** `window.PB` exports the whole state object. | The browser checks read 16 fields of `PB.S`; 20 of the 40 names in `window.PB` are used by no test. `S` has 29 declared fields and 2 more (`lastTap`, `scriptTop`) added at run time. | Query functions (`PB.boards()`, `PB.pageLabels()`) let `S` change shape without touching 14 test files. |
| F9 | **Rendering cost, when it is needed.** A page once drawn stays in the document; `inkChanged` redraws the ink of every drawn page; the Review data and the scene menu are rebuilt on every stroke and every text change. | From reading `syncPages`, `inkChanged`, `updReview`, `updOutline`. Measured at r0: 60 ms to pin a cue on 375 pages. | Fine for 80 to 150 pages (A5). Measure on the laptop before touching it. |
| F10 | **Cue identity.** A cue is its block and its offset in that block. Every popover finds it again after each change. | F5, first line. | No simple fix: an id would have to live in the script text. Recorded so that nobody assumes a cue object outlives an edit. |

## 6. Suggested order

1. **Protect the work:** Q27 and a push; tags (X3).

3. **Device trial of r1.6 and r1.7** (X4), with F7 done first so that thresholds can be tuned on the spot.
4. **X5 and X8**, both small.
5. **Measure a real show's file over a week of revisions** (X6) before deciding anything about the history.

7. **X7** before the next change to a saved format.
